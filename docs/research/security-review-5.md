## MC5-01 — Public-addressed local services bypass the address denylist

**Scenario.** A robot has a globally scoped IPv6 address and a GUI or ROS service listening on that address, and the container has IPv6 connectivity to it. Alternatively, the Docker host has a public IPv4 address, the LAN uses public IPv4 space, or a router hairpins a WAN address/port to a protected service. A tunnel editor supplies that address as the HTTP/TCP origin. Packets leave through the container interface, pass the listed destination exclusions, and hit `policy accept`. No connector code execution or UID change is required.

**Evidence.** Lines 51–52 exclude selected *address classes*, not local machines, local routes or host interfaces. The only IPv6 exclusions are `::/127`, ULA, link-local and multicast; ordinary global IPv6 on the same LAN is accepted. Public IPv4 host addresses likewise do not match the IPv4 set. Host-side DNAT/hairpin translation happens after this namespace's output filter, so it can turn an accepted public destination into a private destination downstream. The same gap applies to uid 65532. The local address-membership check confirmed the exclusions and global-address fallthrough; actual host addresses, host firewall and hairpin behavior were not probed.

The MC4-04 table demonstrates its specific private-address targets. It does not establish protection against other addresses of those same machines. This matters especially for IPv6: a globally scoped address need not be an externally accessible service; host/router rules may admit the robot/container's local source while denying Internet sources.

**Specific fix.** Give the connector a default-drop policy permitting only the required Cloudflare edge destinations/transports, the exact agent endpoint and a constrained DNS endpoint. Give the agent separately scoped relay and GUI permissions. If arbitrary public Internet access remains a requirement, enforce exclusions for all host/site prefixes, host public addresses and hairpin destinations at the host/router boundary where the final destination is known, and maintain those exclusions as addressing changes. Merely adding more special-use prefixes cannot prove “nothing on the LAN or Docker host.” Update MC4-04's isolation claim accordingly.

## MC5-02 — Both bounding-set operations require a missing capability

**Scenario.** Start the example Compose service with exactly its three added capabilities. The outer `setpriv` cannot apply its bounding-set option and exits before starting the agent. Adding `SETPCAP` only for bootstrap is insufficient: once the agent retains only SETUID/SETGID, the inner `setpriv --bounding-set=-all` has the same problem when starting cloudflared.

**Evidence.** Neither the Compose capability list nor the intended agent capabilities contains `CAP_SETPCAP`. [Alpine's setpriv package](https://pkgs.alpinelinux.org/package/v3.22/main/x86_64/setpriv) is util-linux, linked to libcap-ng. In [util-linux 2.41.6 setpriv](https://raw.githubusercontent.com/util-linux/util-linux/v2.41.6/sys-utils/setpriv.c), bounding-set application precedes final capability/ambient handling and execution; failure exits 127. [libcap-ng's implementation](https://raw.githubusercontent.com/stevegrubb/libcap-ng/v0.8.5/src/cap-ng.c) returns an error when the effective set lacks SETPCAP. The kernel independently requires it for [PR_CAPBSET_DROP](https://man7.org/linux/man-pages/man2/PR_CAPBSET_DROP.2const.html).

On the review host, without SETPCAP, both `setpriv --bounding-set=-all /bin/true` and `setpriv --bounding-set=-all,+setuid,+setgid /bin/true` returned 127 with `apply bounding set: Operation not permitted`. This checks the failure mechanism using host util-linux 2.41.3, not the Alpine image. The source/capability mismatch needs reconciliation with the earlier claimed successful image run; no new Docker reproduction was authorized.

This fails closed for network security, but prevents normal service operation. Reordering command-line flags does not change setpriv's internal application order.

**Specific fix.** Remove the bounding-set operations from both invocations, set `--no-new-privs` in the outer entrypoint too, and retain the explicit inheritable/ambient handling. With ordinary non-setuid executables, the outer exec should retain only the two intended capabilities, and the child exec should retain none in permitted/effective/inheritable/ambient sets; validate those actual sets. A nonempty bounding set is not itself an active capability and must not be reported as empty. If an empty child bounding set is mandatory, implement a launcher with an explicit, audited SETPCAP lifecycle rather than adding SETPCAP to the long-lived agent casually. The lifecycle fix in MC5-03 must also be integrated.

## MC5-03 — The agent cannot terminate its different-UID connector

**Scenario.** Once the launcher works and cloudflared is running as 65533, revoke a robot, change its tunnel token, request a restart, or shut down the agent. The supervisor cancels the context, then synchronously waits for its loop to finish. Its default cancellation signal cannot kill the connector, so it can wait until cloudflared exits on its own. A live tunnel process normally runs indefinitely.

**Evidence.** `startLocked` cancels then blocks on `<-s.done` at lines 61–62. The loop is in `cmd.Wait()` at line 108. `exec.CommandContext` uses `Process.Kill`; neither a custom cancellation helper nor CAP_KILL is configured. The agent has uid 65532; setpriv sets the child's real/effective/**saved** uid to 65533. Parentage supplies no signal permission under [kill(2)](https://man7.org/linux/man-pages/man2/kill.2.html); [pidfd_send_signal](https://man7.org/linux/man-pages/man2/pidfd_send_signal.2.html) also checks permission. Retained SETUID/SETGID does not implicitly change the credentials of Go's signal syscall.

The installed Go source confirms that its ten-second WaitDelay retries `Process.Kill`, while `Wait` still awaits process exit. It is not a solution to EPERM. `apply` updates the gateway state **before** calling `sup.Stop` (`main.go:251,262`), so the revoked gateway state is applied; this is not evidence that revoked users retain normal authenticated access. The event loop, subsequent pairing/sync and orderly shutdown can nevertheless stall. The existing tunnel test uses no wrapper and a same-UID fake executable, so its successful restart does not exercise this case. This finding is a source/permission trace, not a cross-UID runtime reproduction here, and becomes reachable after MC5-02 is corrected.

**Specific fix.** Supply an authorized, bounded cancellation path. A small child supervisor retaining only the authority needed to terminate its own capability-free child is one option. Another is retaining CAP_KILL in the agent only, adding it to the Compose/entrypoint capability sets, and ensuring the connector receives none; this permits signaling other container processes and should be an explicit tradeoff. Do not change credentials process-wide around `Kill` in the multithreaded Go agent. Add a real different-UID Stop/Restart/shutdown check with a strict deadline.

## MC5-04 — Connector loopback filtering blocks Docker embedded DNS

**Scenario.** Use the example in a normal Compose network. Docker supplies `nameserver 127.0.0.11`. Cloudflared's UDP DNS query, or TCP fallback, is dropped by the connector loopback rule before the DNS allowance can match. Resolving Cloudflare endpoints consequently fails even though agent-side DNS succeeds.

**Evidence.** [Docker documents](https://docs.docker.com/engine/network/#dns-services) that custom networks use its embedded resolver at `127.0.0.11`; the example no longer selects host networking and joins Compose's network. Line 46 accepts only connector TCP to the agent port. Line 47 drops every other connector loopback packet. The resolver exception appears at line 50. An in-memory shell harness using `127.0.0.11` emitted exactly that ordering; an ordinary UDP DNS query necessarily reaches the drop first. The agent instead reaches the unrestricted loopback acceptance at line 48.

There is a second consideration for the fix: Docker's iptables resolver implementation [DNATs port 53 to its listener port](https://raw.githubusercontent.com/moby/moby/v28.0.0/libnetwork/resolver_unix.go) in output NAT. The current priority 0 runs after standard destination NAT priority -100, as listed in the [nftables manual](https://netfilter.org/projects/nftables/manpage.html). Moving the existing `dport 53` rule upward alone may therefore still miss the translated destination port. That source example is Docker 28; the Docker 29 installation was not inspected.

**Specific fix.** Evaluate a narrowly scoped resolver allowance before the connector loopback drop and before DNS destination NAT, or match the connection's original resolver address/port at the existing hook. Test both UDP and TCP resolution on an actual Compose network, including Docker's embedded resolver. Preserve denial of other loopback destinations/ports. Include IPv6 resolver handling if private/link-local IPv6 resolvers are supported: the current parser emits IPv4 exceptions only.

## MC5-05 — The DNS exception exposes arbitrary TCP/UDP traffic to LAN resolvers

**Scenario.** `/etc/resolv.conf` directly names a LAN router such as `192.168.1.1`. The tunnel editor selects `tcp://192.168.1.1:53`. The connector can relay arbitrary bytes to that router's TCP port 53. An `http://192.168.1.1:53` origin also reaches the port, although a normal DNS server will not produce an HTTP response. This exception can expose a DNS service that trusts local source addresses, and any non-DNS service actually placed on that port.

**Evidence.** The generated rule accepts both TCP and UDP to every configured IPv4 resolver on port 53, for **all UIDs**, before the private-address drop. It does not validate DNS messages or distinguish a resolver lookup from an ingress-origin connection. The shell harness confirmed emission of the permissive rule for the router example. Cloudflared's pinned [TCP origin implementation](https://raw.githubusercontent.com/cloudflare/cloudflared/2026.10.4/ingress/origin_service.go) uses a normal destination dialer. No router HTTP service, DNS vulnerability or unauthorized zone transfer was demonstrated or assumed. An arbitrary HTTP target on a router's port 80 remains blocked by the private-address rule.

This is an intentionally permitted network exception with a broader consequence than “DNS works.” MC4-04 mentions DNS, but its blanket “router blocked” table and residual-risk list omit that remote tunnel users can access the resolver service itself. Under default Compose DNS, MC5-04 currently blocks the stub first; the direct-router case concerns environments that actually put the router address in the container's resolv.conf.

**Specific fix.** Expose a dedicated DNS-only stub to the connector and have that stub validate/forward queries under a separate identity or network boundary. Do not grant the connector direct transport access to the LAN router. If direct resolver access is deliberately retained, state precisely that arbitrary traffic to configured resolver TCP/UDP port 53 is allowed, constrain the resolver's ACL/features accordingly, and include that endpoint in adversarial ingress tests.

## MC5-06 — Upstream parsing grants the wrong HTTPS port and rejects IPv6

**Scenario.** Set `MC_UPSTREAM=https://host.docker.internal` for a private host service. The entrypoint authorizes port 80, while Go's HTTPS transport connects to 443 and is dropped. A valid IPv6 upstream such as `http://[fd00::1]:4006` fails during bootstrap resolution. These are availability/configuration regressions, not unlocked-start bypasses.

**Evidence.** Lines 26–30 discard the scheme and use 80 for every omitted port. The in-memory execution emitted `meta skuid 65532 ip daddr 172.17.0.1 tcp dport 80 accept` for the HTTPS example and proceeded to the agent stub. For the IPv6 example it passed `[fd00::1]` to `getent ahostsv4` and exited with the resolution error. Unbracketed IPv6 is also incompatible with the colon-splitting approach. The Go path uses `url.Parse` (`main.go:202`) and supports HTTPS/WebSocket TLS independently of this shell parser.

**Specific fix.** Parse the URL with one proper parser shared with the agent: validate supported schemes, use `Hostname()`/`Port()`, choose 80/443 correctly, and either resolve/install appropriate rules for the supported address families or reject unsupported ones with an explicit documented constraint. Handle multiple resolved addresses consistently with the dialer. Add checks for HTTP/HTTPS defaults, explicit ports and bracketed IPv6. Explicit IPv4 `http://host:4006` remains the working intended form.

## Checked and sound

- **Private addresses and rebinding.** Assuming successful rule installation, ordinary connector sockets to RFC1918, CGNAT and IPv4 link-local addresses are dropped independently of the chosen hostname, except for the explicit DNS allowance. Rebinding to those addresses supplies no exemption. IPv6 ULA and link-local destinations are likewise dropped. The connector cannot use the agent's GUI allow rule because its socket UID differs. The agent can reach the configured IPv4 GUI address/port, DNS exceptions and public destinations; other listed private destinations/ports remain blocked. It has unrestricted *container* loopback access, not Docker-host loopback access.

- **IPv4-mapped IPv6.** `::ffff:192.168.1.1` is not a demonstrated IPv6-rule bypass. Linux handles mapped connections as IPv4 traffic, so the IPv4 destination exclusions apply. See [Linux IPv6 API semantics](https://man7.org/linux/man-pages/man7/ipv6.7.html). The local prefix check explicitly normalized mapped addresses rather than treating their textual form as proof of escape.

- **NAT64, 6to4 and Teredo limits.** The rules accept `64:ff9b::/96`, network-specific translation prefixes outside the exclusions, `2002::/16` and `2001::/32`. An available translator/relay or configured host tunnel is required for those addresses to lead somewhere else; a literal alone does not create such a path. In particular, [RFC 6052 section 3.1](https://www.rfc-editor.org/rfc/rfc6052.html#section-3.1) requires a conforming well-known-prefix translator to reject embedded non-global IPv4 addresses. Thus `64:ff9b::192.168.1.1` is not a confirmed RFC1918 escape. Network-specific translation into a protected network remains a conditional gap; a ULA translation prefix would already be blocked. 6to4/Teredo are not automatically enabled by this image, and a capability-free process cannot create a raw IP tunnel in the existing network namespace. Known translation/transition paths should be denied or constrained by the MC5-01 policy rather than claiming every such address is exploitable.

- **Multicast, broadcast and protocols.** IPv4 multicast and limited broadcast are included in `224.0.0.0/3`; IPv6 multicast is in `ff00::/8`. Directed broadcast within excluded IPv4 networks is also excluded; public-addressed directed broadcast follows MC5-01. The address drops apply to UDP as well as TCP, including any enabled private-network UDP routing; QUIC to public edges is allowed by the current policy. No CAP_NET_RAW means no ordinary raw/packet sockets. Unprivileged ICMP ping sockets may still be available under the host's ping-group sysctl, but their private IP destinations remain subject to the same output exclusions. Do not equate “no raw capability” with “no possible ICMP.”

- **Socket ownership.** [Kernel nft_meta code](https://raw.githubusercontent.com/torvalds/linux/v6.12/net/netfilter/nft_meta.c) reads socket-file credentials for `skuid`; it is not a userspace-supplied UID label. Ordinary TCP/UDP/QUIC sockets created after the drop carry the connector UID, including helpers inheriting those credentials. Sockets created before a UID change or passed over SCM_RIGHTS can retain the creator's credentials; socketless/generated packets may lack usable socket ownership. The supervisor provides no `ExtraFiles`, preopened network sockets or descriptor-passing service; its inherited standard streams are not an agent network dialer. No reachable ownership-spoofing path was found. The unconditional IP exclusions still cover private destinations when UID matching is unavailable. The `oif lo` whitelist is technically any local address at that TCP port, including `::1`, rather than an exact `127.0.0.1` match; no second privileged service at that port is introduced here.

- **Unix sockets.** Inet nftables rules do not filter pathname or abstract Unix sockets. The supplied Dockerfile/Compose mount no Docker socket, host runtime directory or other service socket, and the agent creates an HTTP listener rather than a Unix listener. `/data` is agent-owned mode 0700, blocking connector traversal, including to any socket there. Abstract Unix sockets share the container's network namespace, not the host's in this configuration. No privileged reachable Unix endpoint is introduced by these files. This is a source/mount review, not an inventory of sockets in a running image; additional socket mounts would change the result. Read-only mounts alone do not prevent connecting to an existing socket.

- **Privilege separation, conditional on fixing the launcher.** The intended child exec clears inherited/ambient capabilities, sets all real/effective/saved IDs to the connector identity, and uses no-new-privs. It cannot regain an earlier saved agent/root identity. No-new-privs prevents setuid/file-capability exec gains; it does not revoke capabilities already held by the agent. Root-owned executable paths are not writable by 65533 in the supplied read-only filesystem, and the private data mount is inaccessible to it. Writable special mounts such as `/dev/shm` do not supply a privileged executable loader in this code. Different credentials and absent SYS_PTRACE/DAC capabilities prevent ordinary ptrace, `/proc/1/mem`, fd/root traversal and protected environment access to the agent. Ordinary destructive signals also require permission; same-session SIGCONT is a limited exception, not privilege escalation. The inverse signal-permission problem is MC5-03.

- **Agent authority.** The agent's retained SETUID/SETGID is real arbitrary identity-changing authority inside its container, including choosing uid 0; calling the agent simply “unprivileged” without that qualification is misleading. No connector-accessible identity-switch RPC, writable helper/configuration, shell interpolation or descriptor service was found. Abusing that authority requires compromising code running with the agent's credentials, or changing trusted startup configuration. With the intended capability drop it cannot recover NET_ADMIN or rewrite the firewall merely by selecting uid 0. A compromised agent already holds robot keys and the trusted GUI path; it is outside this connector-only boundary.

- **Shell failure behavior.** `sh -n agent/entrypoint.sh` passed. A memory-only harness executed the script body with stubbed identity, resolver, nft and final launcher commands: nft exit 7 caused script exit 7 without attempting the agent. `nft` missing would similarly fail the simple command under `set -e`; the here-document does not mask its status. A getent error can be hidden by the pipeline's final awk status, but empty output is explicitly rejected. The `[ ... ] && ...` conditions are valid `set -e` exceptions. Shell variables are not recursively evaluated as shell commands. Inputs interpolated into nft syntax still need to be trusted startup configuration; the resolver parser admits only IPv4-looking numeric strings, not injected nft commands.

- **Initialization, filesystem and overrides.** The create/delete/recreate sequence uses nft's idempotent table-add semantics in one `nft -f` transaction; it is designed to work with the table absent or present, without an unlocked process between separate flush/install commands. Runtime reapplication was not tested here. nft/setpriv need no writable root filesystem for their normal operations; `/data` is the intended persistent writable mount. Unsetting `MC_LISTEN` triggers `set -u` before its apparent port fallback, but the Dockerfile supplies it, and this failure is closed. `MC_EGRESS_LOCK=false` intentionally skips all installation and may leave a fresh namespace completely unlocked; it must be described as an unsafe opt-out for this threat model. Local administrators able to set it can also choose equal/privileged UIDs or host networking, so these trusted overrides are not remote ingress exploits. Validate distinct nonzero UIDs and retain the separate network namespace.

- **Residual-risk wording.** Both existing residuals are valid but incomplete. Redirecting a robot hostname to another agent does not make that agent accept the first robot's audience-bound grant. Redirecting it to an attacker serves attacker-controlled content under the expected robot origin, allowing phishing and receipt of same-origin requests/cookies and bootstrap material; this is more than a cosmetic wrong-origin problem. The relay remains the grant trust root, so account permissions that also allow rewriting the relay/key handling are a separate authorization compromise that this network lock does not solve. Native execution lacks this lock, and so do disabled-lock or inappropriate networking overrides. Add the public/local-address, resolver-service and conditional translation caveats above. No additional High/Critical regression beyond MC5-01 was established in the rest of the commit.

Validation: the focused `GOPROXY=off GOTOOLCHAIN=local /tmp/mowgli-simulator-go/go/bin/go test ./internal/tunnel` passed with Go 1.25.10; its existing case does not cover the wrapper, actual capabilities or different-UID cancellation. `git diff --check 03c1cfe^ 03c1cfe` passed. Shell harnesses ran in memory and did not install rules, invoke the real agent, resolve names or contact services. An attempted isolated user-namespace check stopped at `uid_map: Operation not permitted`; no escalation followed. No new network-namespace, Alpine-image, Docker 29, deployed tunnel or robot-hardware validation is claimed. Only this report was added to the checkout.
