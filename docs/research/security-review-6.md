## MC6-01 — Cloudflare-wide allowances permit application origins, not just tunnel transport

**Scenario.** A tunnel editor changes ingress to `https://admin.owner.example`, an ordinary Cloudflare-proxied service, with the appropriate HTTP Host override if needed. If that hostname resolves into the allowed ranges, the connector can dial its HTTPS listener. A concrete sensitive deployment is an owner's dashboard whose Cloudflare rule admits the site's public NAT address: the connector originates from that site, so the service can admit a request that the editor could not make directly from elsewhere. The origin may be on the owner's LAN behind another tunnel or forwarded port. This requires that service/topology; it does not assume every proxied site lacks authentication.

**Evidence.** Lines 84–85 accept all protocols and ports to the entire published Cloudflare lists, independently of the selected hostname, HTTP Host, SNI, account, or tunnel. For example, `104.16.0.1:443` passes the IPv4 set; the set is not limited to the `198.41.192.*` / `198.41.200.*` tunnel endpoints. Cloudflare documents that its [proxy addresses are shared by proxied hostnames](https://developers.cloudflare.com/fundamentals/concepts/cloudflare-ip-addresses/). Consequently the robot owner's own proxied hostnames are allowed whenever they use these ranges. This contradicts “nothing but the agent” and does not establish the status section's categorical exclusion of other public services/hairpins.

The literals `1.1.1.1` and `1.0.0.1` also receive **all-port/all-protocol** acceptance. The pinned connector's [edge-discovery fallback](https://raw.githubusercontent.com/cloudflare/cloudflared/2026.10.4/edgediscovery/allregions/discovery.go) uses TCP `1.1.1.1:853`; that does not justify every port on both addresses. This is excess permission, not evidence that Cloudflare offers an unauthenticated forwarding service on those addresses. A site routing one of them to a local appliance would also expose that appliance through this allowance.

The generated public-resolver rule separately permits arbitrary TCP/UDP payloads to each configured public IPv4 resolver on port 53. A public-addressed on-site resolver, or a downstream translation to one, can still be reached as an ingress origin. Port filtering is not DNS-message validation. Ordinary Internet recursive resolvers are not automatically sensitive, but the code does not establish that the configured endpoint is one.

**Specific fix.** Separate the agent loopback endpoint, DNS endpoint, and actual tunnel transport. Permit the required [tunnel destinations on TCP/UDP 7844](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/tunnel-with-firewall/), using explicit maintained endpoint sets rather than Cloudflare's whole application-proxy network. Restrict DoT to its required TCP endpoint(s). Use a DNS-only stub for connector resolution if public-addressed local resolvers must also be excluded. Quick-tunnel provisioning and any indispensable HTTPS control traffic need separately justified, narrowly enforced permissions; a shared CDN IP on port 443 is not a hostname boundary. A trusted bootstrap helper or controlled application proxy can separate that traffic from remotely selectable origins. Until then, describe the guarantee as destination-set restriction, and disclose the allowed application/resolver paths.

## MC6-02 — Embedded DNS forwarding to private upstream resolvers remains blocked

**Scenario.** Use the normal Compose network and `nameserver 127.0.0.11`, on a rootful Docker host whose effective upstream resolver is a non-loopback private address such as `192.168.1.1`. Assume no other reachable resolver. Agent and connector queries reach Docker's embedded listener, but external-name forwarding is dropped. The agent then cannot resolve its relay. Internal Docker service-name answers can still work, which can obscure the failure.

**Evidence.** Docker 29's [resolver `dialExtDNS`](https://raw.githubusercontent.com/moby/moby/docker-v29.0.0/daemon/libnetwork/resolver.go) dials a non-HostLoopback upstream inside the sandbox via `backend.ExecFunc`. Its [namespace implementation](https://raw.githubusercontent.com/moby/moby/docker-v29.0.0/daemon/libnetwork/osl/namespace_linux.go) changes the thread's network namespace, not its UID to the requesting container process's UID. On ordinary rootful Docker this forwarding socket is daemon-owned, not uid 65532. Kernel [`skuid` matching](https://raw.githubusercontent.com/torvalds/linux/v6.12/net/netfilter/nft_meta.c) uses the socket file's credentials; it does not propagate the DNS client's identity.

The script reads only the container's resolver file, which in this case contains `127.0.0.11`, not the private external resolver. Its DNS exception also requires uid 65532. A forwarded packet to `192.168.1.1:53` is neither loopback, agent-owned, nor the app-port exception, and is dropped at line 94. The same mechanism covers UDP and TCP. A HostLoopback upstream is dialed in Docker's host context instead, and a public upstream passes the general public-destination policy; these topologies explain why a successful embedded-DNS run does not disprove this case. The actual test-server resolver forwarding path was not inspected here.

This forwarding restriction already existed with embedded DNS in the previous rules: moving the client-to-stub allowance fixes only the first leg. It is a remaining MC5-04 limitation, not a newly introduced UID regression for that topology.

**Specific fix.** Make the embedded resolver's forwarding path part of the deployment configuration. One bounded option is to configure Docker DNS with reachable public resolvers. If private/split DNS is required, explicitly identify the forwarding destination and Docker resolver socket identity and permit only that identity/destination on TCP/UDP 53 **after** the connector jump, or put a DNS-only forwarding stub outside the confined namespace. Do not reopen the connector's direct private-resolver transport. Validate external A/AAAA/SRV queries over UDP and TCP in the private-upstream topology, in addition to the already reported successful topology.

## MC6-03 — Private-address matcher incorrectly excludes public 220–223 resolvers

**Scenario.** A non-embedded resolver configuration supplies Alibaba's public recursive resolvers `223.5.5.5` / `223.6.6.6`. They are misclassified as private, omitted from `public_dns`, and dropped by the connector chain. Normal DNS lookups fail despite the intended public-resolver allowance. This also affects otherwise valid public resolvers in `220.*`, `221.*`, and `222.*`.

**Evidence.** The pattern `2[2-5][0-9].*` matches first octets 220–259, including 220–223. The intended nft exclusion is 224–255. Executing the actual shell function in memory and comparing all 65,536 canonical first/second-octet combinations (`a.b.0.1`) with the script's CIDRs found exactly 1,024 discrepancies: every second octet under 220–223, all overblocking. The complete-script stub harness generated no connector DNS rule for either 223 resolver, while retaining the agent DNS rule and launching the agent stub. Alibaba [documents those addresses as public recursive resolvers](https://www.alibabacloud.com/help/en/dns/public-dns-free-version-access-speed-limit-notification-dns).

The DoT warning is not a complete availability fallback: pinned edge discovery uses DoT for the SRV lookup but then resolves each SRV target through the default `net.LookupIP`. [Quick provisioning](https://raw.githubusercontent.com/cloudflare/cloudflared/2026.10.4/cmd/cloudflared/tunnel/quick_tunnel.go) likewise uses an ordinary HTTP transport. Therefore blocking all usable system resolvers need not leave even named-tunnel startup functional; no live outage is claimed here.

**Specific fix.** At minimum replace that first-octet pattern with `22[4-9].* | 23[0-9].* | 24[0-9].* | 25[0-5].*`. Prefer validating and normalizing four decimal octets before classification and sharing one address-policy representation. Keep checks for 223/224 and 255 boundaries as well as the CGNAT and 172.16/12 boundaries. Verify public-resolver connectivity separately from SRV-only DoT fallback.

## MC6-04 — Public IPv6 nameservers are silently omitted from the connector allowlist

**Scenario.** An otherwise connected dual-stack container without embedded IPv4 DNS has only `nameserver 2001:4860:4860::8888`, a [public IPv6 recursive resolver](https://developers.google.com/speed/public-dns/docs/using) outside the allowed Cloudflare ranges. Before this change, public IPv6 destinations fell through to acceptance. Now all connector queries to this configured resolver are dropped. A numeric IPv4 app target can let bootstrap complete, so this is not necessarily caught by upstream resolution before rule installation.

**Evidence.** The nameserver extraction admits only `[0-9.]+`; both DNS-rule variables are IPv4-only. The complete-script stub harness with only an IPv6 nameserver reached the launcher with both DNS expansions empty. The connector then has no matching exception for the example IPv6 address and hits line 86. The agent can still reach a public IPv6 resolver through its public fallthrough, so agent health alone does not demonstrate connector DNS health. Cloudflare's own public IPv6 resolvers happen to pass its broad range allowance; that does not fix arbitrary public IPv6 DNS. DoT's SRV-only fallback does not replace the missing default resolver path described in MC6-03.

**Specific fix.** Parse resolver addresses by family and generate TCP/UDP 53 rules for permitted public IPv6 resolvers, keeping private/link-local resolver transport excluded for the connector. Alternatively require a working IPv4 DNS stub explicitly and reject unsupported resolver configurations at startup with an accurate diagnostic. Include an IPv6-only nameserver configuration in focused validation; an IPv6 upstream app being unsupported is a separate constraint.

## Checked and sound

- **Ordering and exact agent endpoint.** `meta skuid $CONNECTOR_UID jump connector` precedes the unrestricted loopback rule and both agent exceptions. Every ordinary connector socket therefore enters its own chain, whose final verdict is drop, without falling through to the agent rules. Its permitted agent endpoint is exactly IPv4 `127.0.0.1:$LISTEN_PORT` on loopback/TCP. Destinations outside its explicit agent/DNS/Cloudflare exceptions are denied, including ordinary private IPv4, ULA/link-local IPv6, multicast, and other public destinations. DNS rebinding to a denied address supplies no exemption. Changing the listen address to IPv6-only needs a matching supported policy; the supplied default is IPv4.

- **Embedded DNS conntrack match.** Docker 29's [iptables and native nft resolver NAT source](https://raw.githubusercontent.com/moby/moby/docker-v29.0.0/daemon/libnetwork/resolver_unix.go) maps TCP/UDP `127.0.0.11:53` to TCP/UDP listeners at the same IP and ephemeral ports, with native nft output NAT at dstnat priority. Iptables-nft uses the corresponding output NAT hook. At filter priority 0 the packet's IP is still `127.0.0.11` while its port can be translated; the [kernel conntrack expression](https://raw.githubusercontent.com/torvalds/linux/v6.12/net/netfilter/nft_ct.c) reads the original tuple's port. Thus the rule admits both UDP and TCP, including subsequent tracked packets, under both implementations' normal semantics. Direct connector access to the ephemeral listener port has that ephemeral **original** port and is dropped. This is source verification, not a new runtime test of either backend.

  Adding `ct original ip daddr 127.0.0.11` and `meta l4proto { tcp, udp }` would make the intended tuple/protocol boundary explicit. They are not needed to make the normal Docker UDP/TCP queries work. Without them the rule is formally broader (conntrack `proto-dst` is a protocol tuple field, not DNS validation), but the supplied namespace has no DNAT from other original addresses to this listener, and the capability-free connector cannot install one. No reachable arbitrary-loopback escape was established from these omissions. Do not replace the original-port check with post-DNAT `th dport 53` at this hook.

- **Cloudflare products do not imply automatic private-network access.** The broad sets do contain documented [WARP endpoints](https://developers.cloudflare.com/cloudflare-one/team-and-resources/devices/cloudflare-one-client/deployment/firewall/) such as `162.159.193.0/24`, `162.159.197.0/24`, and `2606:4700:100::/48`, plus application-proxy destinations. This proves transport permission, not that a tunnel editor automatically obtains WARP enrollment or private routes. Spectrum origins are reachable if their actual service IP is allowed and their protocol/authentication permits it; no particular deployment was probed. [Magic WAN/GRE/IPsec](https://developers.cloudflare.com/cloudflare-one/networks/connectivity-options/) requires configured connectivity; allowing a Cloudflare prefix does not create it, and ordinary cloudflared ingress cannot manufacture raw GRE sockets without the needed authority. An ordinary request through a proxied hostname reaches an origin from Cloudflare's IPs, but this alone does **not** bypass Access, WAF, application login, or origin authentication. A “Cloudflare IPs only” origin firewall already assumes additional frontend controls. MC6-01 is about the allowed application path and conditional source/network trust, not a universal Cloudflare authentication bypass.

- **Agent's wider network authority is an explicit trust boundary.** The agent retains public IPv4/global IPv6 fallthrough, including public-addressed host/site destinations and downstream translations. This is acceptable for a boundary against a tunnel editor controlling a capability-free connector, provided the claim is limited accordingly: the gateway fixes the HTTP upstream with `SetURL`, and its WebSocket target also comes from trusted configuration; ingress does not supply an arbitrary agent dial destination. A compromised agent or relay capable of replacing authorization/keys is outside that assumption. A stronger “even a compromised agent cannot reach the host/site” requirement is not implemented.

- **KILL scope and no-new-privs.** CAP_KILL lets the agent signal different-UID processes throughout its visible PID namespace, not just cloudflared; that includes other container processes added by an operator. The supplied Compose service has its own PID namespace and exposes no host PID handles or host PID mode. No new path to signal host/ROS processes follows. The agent already possesses arbitrary UID/GID-changing authority and the robot keys; KILL is a deliberate lifecycle privilege within that trusted container. The inner launcher clears inheritable and ambient caps before executing as uid 65533. Its retained bounding set grants no active KILL/SETUID/NET_ADMIN capability. No-new-privs [prevents new exec-derived privileges but does not revoke held privileges](https://docs.kernel.org/userspace-api/no_new_privs.html); retaining the agent's existing ambient caps is compatible with it. The [ambient/exec rules](https://man7.org/linux/man-pages/man7/capabilities.7.html) permit the intended agent sets and clear the child's active sets on ordinary exec. No connector-accessible credential-changing or signal RPC, saved agent/root identity, or writable privileged helper was found. Changing UID alone does not recover the agent's dropped NET_ADMIN under no-new-privs.

- **Shell robustness and resolver text.** `sh -n` passes. An in-memory complete-script harness replaced identity/resolution, `/etc/resolv.conf` reads, nft, and the final launcher with stubs. Empty DNS variables produce blank here-doc lines, not empty nft sets or shell execution. No-resolver, IPv6-only, private-only, embedded, and public-resolver inputs all reached the stub launcher; a stub nft exit 7 stopped execution with exit 7 before launching. The `[ ... ] && assignment` and `||` conditions do not trip `set -e`. No real nft grammar/kernel acceptance was exercised by the stubs. A failed getent can be masked by the pipeline's awk status, but empty resolution is explicitly rejected. Nonempty `options`/`search` lines and comments are ignored by the nameserver extractor. Tabs/trailing whitespace/comments on a valid embedded-nameserver line can trigger a false warning because the separate grep requires an exact line; the allowance itself is unconditional and still present, so this is diagnostic noise, not an egress defect.

- **Matcher boundaries and malformed input.** The actual shell function correctly classifies canonical `100.64.0.0`–`100.127.255.255`, `172.16.0.0`–`172.31.255.255`, and 224–255, with the adjacent canonical boundaries correctly excluded from those ranges. Its overblocking is MC6-03. It is not an IPv4 validator: for example `999.1.2.3`, `...`, and zero-padded octets can fall through as “public,” while `192.168.999.999` returns “private.” The awk numeric/dot filter excludes nft command injection, but does not normalize or validate addresses. Rejected nft input stops startup; alternate numeric spellings accepted by a particular nft/libc parser need normalization before this classification, not an assumption that every malformed-looking string fails. No alternate-notation bypass was verified here, and resolv.conf/startup environment are not controlled by tunnel ingress in these files.

- **Filesystem and opt-outs.** The separate network/PID namespaces, read-only image, root-owned launchers, distinct UIDs, and agent-only 0700 data directory remain part of the boundary. No Docker socket, host service socket, preopened agent network descriptor, or connector-writable privileged configuration was introduced. `MC_EGRESS_LOCK=false`, equal/privileged UID overrides, expanded allow sets, and host networking remain trusted administrator changes that can invalidate it; none is reachable merely by editing tunnel ingress. The new `MC_LISTEN` default removes the previous unset-variable startup failure.
