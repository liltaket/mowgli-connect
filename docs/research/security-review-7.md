## MC6-01 — Edge, DoT, and quick-mode exceptions

**Named mode.** Lines 88–90 permit TCP/UDP destination port 7844 to `198.41.192.0/24`, `198.41.200.0/24`, `2606:4700:a0::/48`, and `2606:4700:a8::/48`, and TCP destination port 853 to `1.1.1.1`/`1.0.0.1`. TCP 443 is absent. This replaces the previous all-port, whole-proxy-network permission and removes direct connector access to configured public resolvers on port 53.

Cloudflare's [firewall documentation](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/tunnel-with-firewall/) identifies endpoints within these prefixes as Tunnel transport on TCP/UDP 7844. An ingress such as `tcp://198.41.192.167:7844` is **packet-reachable**: a visitor could send bytes to the edge through it. That does not make it a usable route to a chosen robot/LAN origin. The documented listener terminates the tunnel protocol, not an ordinary hostname-selected website or an unauthenticated generic CONNECT/SOCKS proxy. Even carrying another connector's authenticated tunnel handshake through that byte stream does not execute its origin dialer on this robot; the connecting endpoint handles that tunnel's origin streams. No additional listener/service was identified that turns those bytes into attacker-selected connections from the robot.

These are prefixes, not an inventory of every listener. No scan or proof that every address is forever dedicated to Tunnel was performed. Another service on an allowed address/port, a future reassignment, or local routing/DNAT that repurposes an allowed tuple would change the conclusion. Mere permission to send bytes to an edge service is insufficient to retain MC6-01 as an application-origin escape.

**DoT.** [Cloudflare documents](https://developers.cloudflare.com/1.1.1.1/encryption/dns-over-tls/) both permitted endpoints as DNS over TLS on TCP 853. Arbitrary connector bytes can reach that port, but successful application use requires the service's TLS/DNS protocol. There is no demonstrated generic byte-forwarding or local-network proxy there. DNS queries and their answers remain possible, including queries involving attacker-controlled authoritative DNS; this is not a guarantee against DNS-based communication. TCP 80/443, UDP 853, and unrelated ports on those two IPs are denied in named mode. The additional `1.0.0.1:853` permission is a second documented DoT endpoint, although pinned edge discovery uses `1.1.1.1:853`.

**Quick mode.** Lines 77–79 do genuinely grant TCP 443 to the whole Cloudflare proxy address list, without hostname/SNI restriction. The rule itself would permit arbitrary proxied HTTPS origins **if the connector were made to dial them**. However, `main.go:243`/`:253` selects quick mode from trusted local configuration and always passes `QuickURL: "http://" + cfg.listen`; the relay's `TunnelToken` is ignored in this branch. `supervisor.go:81`–`:86` then uses `--url`, without a named-tunnel token. [Quick Tunnels are accountless](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/); the [pinned quick provisioner](https://raw.githubusercontent.com/cloudflare/cloudflared/2026.10.4/cmd/cloudflared/tunnel/quick_tunnel.go) obtains its credentials from the quick service. Control of the user's account/relay is not control of that Cloudflare-operated provisioning service or its TLS identity. No account-editable origin or local quick-service setting is supplied by relay state. Changing Host, DNS, grants, or the relay's token does not change this local origin.

Thus quick HTTPS is not a demonstrated account-level ingress escape. Its protection is partly cloudflared's local quick-mode behavior, not solely nft's destination restriction. Connector code execution, trusted local configuration changes, or compromise of the quick provisioning service is a different threat and would expose that wider HTTPS permission. Named mode has the stronger packet boundary.

## MC6-02 and MC5-04 — Root DNS sockets and embedded DNS

The output chain jumps connector-owned sockets to `connector` at line 96. That chain accepts specific endpoints or drops at line 92; it never returns to the unrestricted loopback, agent, or root exceptions. In particular, a connector socket to `192.168.1.1:53` cannot reach line 103 just because that line permits uid 0.

[Docker 29's resolver](https://raw.githubusercontent.com/moby/moby/docker-v29.0.0/daemon/libnetwork/resolver.go) creates its non-host-loopback upstream connection in the sandbox via `backend.ExecFunc`, then exchanges parsed DNS messages. On normal rootful Docker this is a root-owned socket rather than a connector-owned socket. The new exception admits both transports to a private upstream, fixing the second leg. Host-loopback forwarding runs in Docker's host context and does not depend on this namespace's rule. The lead reports external resolution through `--dns 172.17.0.1` while direct connector queries to that resolver failed. This is relevant container evidence, not independently repeated evidence or proof of every resolver/backend/transport topology.

For the first leg, [Docker's NAT implementation](https://raw.githubusercontent.com/moby/moby/docker-v29.0.0/daemon/libnetwork/resolver_unix.go) maps TCP/UDP `127.0.0.11:53` to listeners at that IP with different ports. Output filter priority 0 follows destination NAT. Line 87 matches the post-NAT IP and **original conntrack port**, so the intended queries pass. It does not run before DNAT, despite the comments' wording. Directly dialing the ephemeral listener port has a different original port and is denied. The newly explicit TCP/UDP protocol guard is sound.

**Who can create uid-0 sockets after startup?**

- Docker's rootful embedded resolver can, while executing in the network namespace.
- An operator can launch a root process with Docker exec; the entrypoint does not constrain that separately launched process. Such an operator already controls container administration. An external root process entering the namespace likewise is outside this remote-account boundary.
- The agent retains CAP_SETUID/CAP_SETGID/KILL at lines 115–116. Compromised agent code can select uid/fsuid 0 before creating a socket and use the new exception to send arbitrary TCP/UDP bytes to **any** address on port 53, including private/link-local addresses not listed as resolvers. No-new-privileges does not revoke capabilities already held. Consequently the comment “no process here runs as root after start-up” must not be read as an enforced inability to become root.
- The capability-free connector has no saved root/agent UID, no credential-changing RPC, no preopened root network socket/descriptor-passing path in the supervisor, and no demonstrated route to those capabilities. An account/relay change supplies data, not a CAP_SETUID syscall in the agent. Merely sending a request to the agent creates any resulting outbound socket under the agent's credentials, not uid 0.

The root rule is wider than “only Docker's configured resolver destinations,” but it is **not a new connector bypass** under the stated threat. It is a real residual expansion for compromised trusted agent code, plus administrative root processes. Selecting uid 0 alone does not restore the agent's dropped NET_ADMIN under the supplied no-new-privileges launch, so this observation is not a demonstrated ability to rewrite the firewall.

The embedded stub is a DNS parser/forwarder, not a raw transport proxy. A tunnel origin can nevertheless expose `tcp://127.0.0.11:53` to DNS-speaking clients: allowed DNS questions, internal/split DNS answers, and forwarded queries to the configured private resolver are intentional residual reachability. This lock cannot promise that the connector never interacts with LAN DNS **through DNS**. It prevents its direct arbitrary-byte LAN resolver connection; it does not remove the DNS service's own attack surface or query semantics.

## MC6-04 — IPv6 addresses and scope zones

Lines 65–73 collect colon-containing nameservers into an IPv6 set for the **agent** on TCP/UDP 53. The actual POSIX/BusyBox expansion `${ns%%%*}` correctly turns `fe80::1%eth0` into `fe80::1`, leaves unscoped addresses intact, and also strips a numeric zone such as `%12`. Generated nft addresses must omit `%iface`: interface scope is socket/routing information, not part of the packet's IPv6 destination address.

The script does not rewrite `/etc/resolv.conf`; a resolver implementation supporting scoped literals retains the original zone when creating its socket. For example, [Go's resolver parser](https://raw.githubusercontent.com/golang/go/go1.25.0/src/net/dnsconfig_unix.go) accepts the literal with `netip.ParseAddr` and retains it in the server endpoint. A packet sent via the named interface still has destination `fe80::1`, so the emitted address match does not break it. Lack of an output-interface predicate also permits that same address on other interfaces for the agent; this is not exact interface-scoped authorization. Missing/nonexistent scope or unsuitable interface/routing still fails at the client/network, not because nft needs a zone suffix.

Global IPv6, ULA, and scoped link-local agent DNS allowances now render correctly. No live IPv6 reachability, neighbor discovery, or interface/backend behavior was tested. Most importantly, these are agent-only exceptions: a connector configured solely with `2001:4860:4860::8888` or `fe80::1%eth0` still reaches its terminal drop. MC6-04 is therefore only partially fixed, rather than closed by the agent's new IPv6 line.

## MC7-01 — Non-embedded resolver configurations lose connector DNS

**Scenario.** Run the locked image on a Docker bridge/configuration whose `/etc/resolv.conf` lists a public IPv4 resolver such as `8.8.8.8` directly, without `127.0.0.11`. Use a numeric IPv4 app upstream so root bootstrap resolution does not obscure the failure. Before this patch, configured public IPv4 DNS was permitted for the connector. Now every UDP/TCP query to that resolver is dropped, while the agent's queries work. An IPv6-only nameserver setup retains the MC6-04 failure. A normal user-defined Compose network with embedded DNS does not have this problem.

**Evidence.** The connector contains no direct DNS exception and ends in `drop` (`entrypoint.sh:85`–`:92`). The absence check at lines 74–75 only warns that cloudflared “will rely on DNS-over-TLS”; startup continues. In [pinned cloudflared discovery](https://raw.githubusercontent.com/cloudflare/cloudflared/2026.10.4/edgediscovery/allregions/discovery.go), the private DoT resolver is used for the SRV fallback, but `resolveSRV` subsequently calls the ordinary `net.LookupIP` on each target. Allowing DoT therefore does not supply the missing A/AAAA lookup. Quick provisioning likewise needs ordinary hostname resolution for its HTTPS service. With no usable hosts-file overrides or other resolver path, a fresh connector cannot start normally.

The complete-script stub harness confirmed that direct-public-IPv4, direct-public-IPv6, scoped-link-local, and empty-resolver configurations all proceed to the launcher with no connector DNS rule. This proves rule generation and failure to reject; upstream source supplies the incomplete-fallback reasoning. It is not a new live cloudflared outage reproduction.

**Impact.** Remote access becomes unavailable in these configurations; the agent can still register/poll, making agent health misleading. This is an availability defect, not permission to access a blocked target. Existing direct public IPv4 deployments regress; the recommended embedded-DNS deployment remains supported.

**Specific fix.** Either provide a DNS-only resolver path usable by the connector for all necessary lookups, or make a working embedded stub an explicit required deployment precondition and fail startup with an accurate explanation when it is absent. Update stale deployment wording about public resolver access. Do not reopen raw connector access to a LAN/public-addressed local resolver just to silence the error. Validate both ordinary A/AAAA and SRV resolution, including quick provisioning, for any claimed fallback.

## MC5-01 and overall verdict — Account plus relay compromise

**The narrow connector lock now works by destination/port under trusted startup and ordinary routing.** A malicious named-tunnel editor can send connector traffic to `127.0.0.1:$LISTEN_PORT` (default 4007), the embedded DNS service, the listed edge prefixes on TCP/UDP 7844, and the two DoT endpoints on TCP 853. It cannot directly dial other container loopback services, the app at its host-gateway address, arbitrary host/LAN/router/CGNAT/link-local services, global IPv6 LAN services, multicast, ordinary public services, or Cloudflare-proxied websites. Public-address hairpins and translation destinations outside the explicit allowlist are blocked too. DNS rebinding does not bypass destination filtering. The qualifications about repurposed allowed tuples above remain.

**Full relay control still grants owner access to the configured robot app.** `main.go:170`–`:184` and `:251` accept relay-provided signing keys, hostname, membership roles, and epoch. An attacker controlling that relay can keep state fresh, add themselves as owner, and issue a correctly audience/issuer-bound grant. Host/Origin checks do not stop that attacker: they control the expected hostname and can make a same-origin or non-browser request. HTTP and WebSocket targets remain fixed to `MC_UPSTREAM` (`gateway.go:120`–`:123`, `ws.go:29`–`:41`), but owner policy permits the upstream API surface except the local teleop publish-WebSocket gate when disabled (`policy.go:77`–`:83`).

This is privileged robot administration, not merely the ability to view the GUI. Existing [GUI traffic research](mowgli-gui-traffic.md) identifies settings/credential reads, settings writes, ROS service calls, container management, firmware/update, and reboot/shutdown routes. The actual deployed GUI revision/features determine the available operations. Disabling teleop blocks that specific publish socket; it is not a blanket ban on motion, blade, configuration, or other administrative commands. The network lock does not protect the robot from a malicious grant trust root or from actions/transitive networking exposed by the allowed upstream application. No physical execution or arbitrary-shell result was tested here.

**The relay can also cause limited HTTP requests under the agent UID without exploiting code.** `relay/client.go:115`–`:119` constructs a default `http.Client` with no redirect policy, and [Go follows redirects by default](https://raw.githubusercontent.com/golang/go/go1.25.0/src/net/http/client.go). For example, a malicious `/v1/robots/self` response can return `302 Location: http://<public-addressed-site-service>:<port>/<path>`. The agent attempts the redirected GET before trying to decode the final relay JSON. A non-JSON response does not undo the request. In quick mode the relay-controlled hostname and redirect-following health check (`main.go:401`–`:414`) provide a further HTTP request surface.

Those agent sockets can reach public IPv4/global IPv6 destinations, including public-addressed host/LAN services and downstream hairpins; any container loopback port; the pinned IPv4 app address/TCP port; and configured IPv4/IPv6 resolver addresses on TCP 53. The latter rule also allows UDP for normal DNS, but HTTP redirects do not create arbitrary UDP traffic. This is constrained HTTP(S) request capability, **not** a generic raw TCP/UDP proxy or automatic response exfiltration to the relay. Ordinary HTTP client protocol, TLS verification, method/body/redirect rules and the destination service still apply. Other private destination ports remain dropped. This pre-existing agent authority keeps MC5-01 PARTIAL for the combined attacker specified in this review; it is not introduced by aee1e2d.

**Remaining boundaries and residual risks.**

- Account/relay control alone does not provide agent code execution, CAP_SETUID, root-owned arbitrary sockets, firewall mutation, arbitrary command execution in this container, or direct arbitrary host/LAN transport. No such escalation was established. Agent code execution would be a separate compromise: its robot keys, public/loopback/app/DNS authority and identity-changing capabilities then make its boundary much weaker; the new root rule adds any destination on TCP/UDP 53.
- A forged owner session can use the app's privileged features and any further networking or administration they perform outside this container. Therefore “cannot directly dial other LAN ports from cloudflared” must not be restated as “cannot affect other robot services” or “safe against full account/relay compromise.” Separate app authentication/authorization rooted independently of the relay would be needed for that stronger claim.
- The account can repoint the robot hostname, serve attacker content, obtain same-origin browser requests/cookies/bootstrap material, and phish users. It can disrupt/revoke/replace tunnels, withhold relay freshness, or flood permitted surfaces. This filter provides no availability guarantee or application vulnerability protection.
- Embedded and DoT DNS remain usable DNS services; permitted queries and DNS-mediated communication are residual access. The root exception does not expose a direct connector-to-private-resolver byte stream.
- Destination restrictions assume the supplied separate network/PID namespaces, distinct nonzero UIDs, fixed trusted upstream, read-only image, protected data directory, and no privileged socket mounts/passed descriptors. Native execution, disabled lock, expanded `MC_EDGE_V4/V6`, UID collisions, host networking, new mounts/helpers, or host routing that repurposes allowed destinations changes the claim. The agent's public-destination policy is not a comprehensive site-prefix or translation boundary.
- Quick mode's full Cloudflare HTTPS access is an intentional larger packet permission, held safe against account-level ingress rewriting by the local quick origin. It does not promise the same confinement after connector code execution. Trust in Cloudflare's actual edge/DoT/quick services remains.

## Checked and sound

- **Empty nft expansions and shell failure behavior.** Empty `quick_https`, `agent_dns4`, and `agent_dns6` become blank lines, not empty sets, commands, or missing braces. All are initialized before use with `set -u`. False `[ ... ] && assignment` conditions and the grep/echo alternative do not trigger `set -e`. A stub nft exit 7 stops the script with exit 7 before agent launch. A failing real nft remains a simple command under `set -e`; no unlocked launch path was found. The create/delete/recreate transaction is unchanged.
- **Rule ordering.** The connector's terminal chain precedes unrestricted loopback and every agent/root exception. TCP 853 and edge TCP/UDP 7844 do not grant other ports/protocols. Named mode has no TCP 443 rule. The agent app permission is still a single resolved IPv4 address and TCP port; no relay field changes that rule. Bootstrap parsing/multi-address/DNS-change limitations from review 6 remain trusted-configuration availability caveats.
- **IPv6 scope handling.** Global, ULA, `%eth0`, and numeric `%12` examples produce unscoped nft IPv6 literals for agent DNS, retaining the original resolver file for the client. No accidental IPv4-family rule or percent-bearing nft address was generated. Interface-specific reachability is unverified; stripping the zone itself is not a confirmed defect.
- **UID and capability separation.** Ordinary connector sockets have the connector's kernel socket credentials. Clearing its inherited/ambient capabilities and executing with all IDs set to the separate connector UID still prevents selecting root or the agent UID. Retained bounding bits are not active capabilities, and no-new-privileges prevents exec-derived gains; “all capability sets zero” must still not include an uncleared bounding set. The agent retains real SETUID/SETGID/KILL authority, as explicitly qualified above. No connector-accessible privileged socket/helper or descriptor handoff was introduced.
- **No assumed service behind a permitted IP.** The broad-prefix edge allowance is an actual packet permission, but an actionable application-origin bypass requires a usable listener/protocol/path. No open proxy or other such service was established on these 7844 tuples. Neither generic Spectrum/WARP/GRE availability nor a recursive tunnel origin was assumed to manufacture robot-local reachability.

## Validation and evidence limits

- `sh -n agent/entrypoint.sh`, `busybox sh -n agent/entrypoint.sh`, and `git diff --check abdaa87 aee1e2d` passed. ShellCheck reported only SC2013 (informational advice about iterating awk output); no shell correctness defect follows from splitting whitespace-delimited nameserver tokens here.
- An in-memory complete-script harness ran nine scenarios on both `/bin/sh` and BusyBox sh: unset/named mode with empty DNS, embedded DNS, direct `223.5.5.5`, direct global IPv6, link-local `%eth0`, link-local `%12`, mixed private IPv4/IPv6, quick mode with embedded DNS, and nft failure. All 18 expected exit/launch/rule-generation assertions passed. Identity, resolver-file reads, upstream resolution, nft, and the final launcher were stubbed. No real rules, agent, setpriv, DNS, listener, or network-namespace changes were executed.
- The local nft executable could not initialize its Netlink socket (`Operation not permitted`, even for the attempted version query). No escalation followed. The harness is not proof of image nft grammar/kernel acceptance. Blank-line syntax/order inspection and the lead's reported successful named-mode run support the conclusions; quick-mode and IPv6 runtime acceptance were not demonstrated here.
- The lead reports four edge connections, grant access to a stand-in GUI, rejection of the listed pushed application origins, and a working private upstream DNS forwarder while direct connector DNS was blocked. These support the named-mode/private-forwarding fixes. They do not independently establish forced DNS-over-TCP behavior on each Docker backend, quick-mode behavior, a full edge listener inventory, IPv6 networking, ARM64 image behavior, or physical robot safety.

Overall: the named connector is now confined to the intended agent/DNS/tunnel service tuples, with no demonstrated account-edited-ingress escape. Non-embedded DNS remains an availability defect. Full relay compromise still authorizes privileged robot-app access and can exercise the agent's wider HTTP egress; the lock is not a defense against that grant trust root.

## Status after fixes (lead, 2026-11-08)

- **MC7-01 / MC6-04.** With the lock on, the entrypoint now refuses to start without Docker's
  embedded DNS (127.0.0.11), and its message names the fix: a user-defined or Compose network.
  It no longer starts a connector that cannot resolve the edge.
- **MC5-01, relay-driven agent requests.** The relay client and the quick-tunnel health check
  no longer follow redirects (`relay.NoRedirectClient`, covered by `TestNoRedirectClient`). A
  malicious relay therefore cannot bounce agent requests to other addresses. Only the
  configured relay URL and the relay-supplied robot hostname remain request targets.
- **Accepted residual risk, unchanged and documented.** Whoever controls the relay and the
  account is the root of trust for grants. That party gets owner access to the robot app and
  can repoint or phish the robot hostname. It cannot reach the robot OS, other robot services
  or the LAN through the connector.
