## MC4-01 — Replay persistence fails open or loses live records

**Problem.** Persisting grant consumption is now part of an authentication guarantee, but `persistLocked` still treats failures as a warning and returns no error (`sessions.go:61–82`). `redeemGrant` returns a usable session after this call regardless of its result (`gateway.go:375–379`). Separately, the loader retains at most `maxSessions * 4` replay IDs (`sessions.go:44–47`), while `redeemGrant` adds IDs without an equivalent bound. Session count is not a bound on consumed grants: logging out frees sessions but retains their live replay IDs, and a grant rejected at the full-session check has already entered the JTI map.

**Concrete scenario.** The data volume becomes unwritable/full, a legitimate grant is redeemed successfully, and the process restarts within approximately 30 seconds of issuance. After fresh relay synchronization, someone holding a copy of that grant can redeem it again. No volume writer is required: an ordinary storage failure suffices. The other path requires unusually heavy authenticated grant activity: more than 4096 live IDs are serialized, then a restart drops arbitrary entries due to map iteration order. A copied grant whose ID was dropped can likewise be replayed if its issuance passes the startup cutoff. These are the same leaked-grant, short-restart-window preconditions as MC3-05, not signature forgery or epoch bypass. The overflow case is less likely at this prototype's scale.

**Evidence.** No-listener Go checks used the real `redeemGrant`, `New`, and loader. Normal persisted redemption was rejected on restart and legacy session arrays loaded correctly. With a session path in a nonexistent directory, redemption succeeded, logged the write failure, and the identical grant succeeded after restart and fresh state. This injects a deterministic file-creation error; it does not simulate a full physical disk. A separate valid-format file with 4097 unexpired replay IDs restored exactly 4096; a valid signed grant carrying the omitted ID was accepted. That check establishes loader behavior, not a measured 4097-login workload. `TestGrantNotReusableAfterRestart` covers neither error nor overflow.

**Specific fix.** Return persistence errors and refuse to issue a session until grant consumption has been committed successfully. Reconcile runtime and loader capacity: enforce a bound before accepting additional grants, and never silently omit still-live consumption records. On unreadable/over-cap replay state, fail closed for pre-start grants or require a new post-start grant. Retain old-format session compatibility with an explicit upgrade policy. Add write-failure and capacity/restart tests. If power-loss durability is claimed, sync the temporary file and directory around rename as well; atomic replacement alone is not that durability guarantee.

## MC4-02 — A hostname retry becomes a poll, then loses its retry deadline

**Problem.** A failed hostname report shortens `nextPoll` to request a retry in ten seconds. When that deadline expires, the code retries the report and also treats it as a due `/self` poll. The subsequent assignment `nextPoll = time.Now().Add(wait)` overwrites the reporting retry with the ordinary poll interval. This couples the two schedules that the restructuring intended to separate.

**Concrete scenario.** A claimed Quick Tunnel changes hostname. Its report fails transiently while the next `/self` poll is far in the future. The agent retries after ten seconds, but if that attempt also fails while `/self` succeeds, the next retry waits until another event or the three-minute poll deadline. With a health tick two minutes away, there can be nearly two minutes with the old/unset hostname still published instead of ten seconds. While `pendingHost` is nonempty, the health self-check is deliberately skipped. No unauthenticated party can submit a hostname directly; this is an availability and request-budget regression during reporting failures.

**Evidence.** Exact control-flow trace, not a running event-loop test: assume a successful poll at t=0 sets `nextPoll=180 s`, and the hostname arrives at t=5 s. A failed report sets `nextPoll=15 s` at lines 288–289. At t=15 s another failure proposes t=25 s, which is not before the already-due t=15 s, so the deadline is unchanged. Line 298 runs `/self`; on success line 344 sets the deadline to t=195 s. A later health event can wake reporting earlier, but does not preserve the promised ten-second retry. A resync during a pending retry can also replace its shortened deadline. There is no committed main-loop test for these interactions.

**Specific fix.** Track `nextHostnameReport` independently from `nextPoll`. Only a due relay poll or queued resync should run `/self`; only a due reporting deadline or a newly announced hostname should report. Wait for the earliest outstanding deadline plus existing event channels. Add fake-clock cases for repeated report failures with successful `/self`, health-only wakes, resync during a pending retry, and the unclaimed fast-poll transition. The current loop has no demonstrated busy loop or lost resync request: waiters received during a poll remain queued and force another iteration, and all selected waiters are closed after the poll attempt.

## MC4-03 — Return-path expansion breaks cookie-only OAuth login

**Problem.** Moving the full return path into the cookie introduces a browser storage bound. `safeReturnPath` validates its syntax but does not limit length; `encodeLoginState` base64url-expands the complete UTF-8 path (`oauth.ts:27–28,47`). A valid long path therefore creates a cookie exceeding 4096 bytes. Cookie parsing/storage rejects name-plus-value lengths above 4096 in the [HTTP cookie specification draft, sections 5.6–5.7](https://www.ietf.org/archive/id/draft-ietf-httpbis-rfc6265bis-22.html#section-5.6).

**Concrete scenario.** A logged-out user follows `/login?return_to=` with a local path of several kilobytes, or `/open/<robotId>?padding=...`, whose complete path/query is carried by `loginRedirect`. The relay sends the GitHub authorization redirect with an oversized cookie. A browser rejecting that cookie later returns with no matching login state (or an older cookie), and the callback returns 400 after the user completes GitHub authentication. Starting again from `/login` without the long return path recovers. This affects the selected login attempt, not an already authenticated session or other users.

**Evidence.** A direct call to committed `startLogin` with `"/" + "x".repeat(4000)` emitted **5504 bytes** in Set-Cookie; the cookie name and value alone were **5450 bytes** (5451 including `=`). Modeling the specified rejection by omitting this cookie made `finishLogin` return 400 before any external fetch or database access. Oversize header production and the callback failure are locally confirmed; no real browser was run. Existing OAuth tests use short return paths and therefore miss this new constraint.

**Specific fix.** Limit the UTF-8 return path before encoding, or fall back to `/` when the complete encoded cookie would exceed a conservative size budget. Prefer this fallback over cutting a URL mid-escape. Bound decode input too. Add tests using long ASCII and multibyte return paths, verifying the actual serialized cookie size and a successful safe fallback login.

## Remaining MC3-04 gap — public write admission

The precheck and final INSERT solve different problems. Deriving the precheck identity from the supplied public key is sound because assertion verification independently requires `iss == deriveRobotId(raw)` and a valid signature using that same key. An attacker cannot select an existing victim robot merely by supplying its ID. The final `INSERT ... SELECT ... WHERE count < cap` is a single atomic SQL statement; no concurrent robot-row-cap bypass was established. Sequential requests at capacity reject unknown robots without recording their assertion, while a known unclaimed robot re-registers successfully. A parallel initial registration of the *same* identity can return 429 for the losing request due to `INSERT OR IGNORE`; retry then takes the existing-robot path, so this is not a lasting re-registration lockout.

However, the replay INSERT at `robotApi.ts:43` remains outside that atomic admission decision. A local in-memory SQLite D1 adapter ran the committed Worker with a barrier making four initial COUNT queries observe zero. With a cap of one, statuses were **200, 429, 429, 429**, with **one robot and four JTI rows**. This demonstrates an admissible request interleaving, not a deployed D1 concurrency/load test. The existing sequential test correctly asserts its narrower case but cannot establish that all denied admissions write nothing.

In addition, ten sequential re-registrations by the one admitted self-created identity all returned 200 and added ten replay rows, plus pairing-code writes. That path needs no allowed GitHub user and is explicitly exempted from the new-robot cap. No per-identity/source/global write-admission budget exists. Rejecting those identities altogether would break legitimate re-registration; apply a bounded refresh budget instead. Place final new-row admission and replay consumption in one conditional transaction/batch whose denied result leaves no replay row, and test concurrent denial. Application budgets still cannot protect Worker invocation quota. The lead's stated separate-account acceptance limits the blast radius of that residual quota risk; it does not make these application writes bounded. This is an unresolved part of MC3-04, not another independently numbered vulnerability.

## Checked and sound within scope

- **Login binding.** In prefix-aware browsers, Secure/HttpOnly host-only `__Host-mcr_oauth`, random 256-bit state/verifier, exact state matching, PKCE S256, provider identity lookup, and the allow list resist login CSRF/fixation. A signature is not required against foreign websites unable to plant this cookie; modifying one's own HTTP cookie does not impersonate another user. See [cookie prefix requirements](https://www.ietf.org/archive/id/draft-ietf-httpbis-rfc6265bis-22.html#section-4.1.3.2).
- **OAuth replay and return path.** Expired/malformed cookies fail; expiry extension requires cookie tampering. Callbacks clear the cookie, with replay rejection now relying on provider code single use. [GitHub requires the original PKCE verifier](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps). Local stubs checked replay and verifier matching; committed stubs check single use but not challenge/verifier correspondence. Decoded return paths are revalidated, blocking foreign schemes, `//`, raw backslashes/controls; encoded slashes remain path data. No open redirect was established. Size is MC4-03.
- **CSRF edge cases.** Exact Origin works without metadata. Missing/`null` Origin needs exact `same-origin` metadata; foreign non-null Origin cannot use it. Older browsers missing both fail closed. Opaque sandbox/`data:` origins do not qualify; redirects retain foreign provenance, and browser script cannot forge `Sec-` headers. These are [specification-based conclusions](https://www.w3.org/TR/fetch-metadata/#sec-fetch-site-header), not browser tests. The [Fetch Origin algorithm](https://fetch.spec.whatwg.org/#append-a-request-origin-header) supports the no-referrer/form explanation. `same-origin` referrer policy suppresses foreign referrers; agent WebSockets still require real Origin. Non-browser clients still need credentials despite being able to spoof headers.
- **Separate sites.** Robots under `trycloudflare.com` or the later robot zone remain foreign to the relay under `workers.dev`; the fallback requires same-origin, not same-site. The relay opens a callback GET, whose robot document makes its own same-origin session POST. A robot page gains no relay-mutation exception.
- **Resources.** Body bytes retained by the helper are bounded; receive time and runtime chunk allocation are not. Oversize HTML preserves bytes/metadata and close ownership. Successful rewrite/pass-through paths closed the original exactly once in direct checks. Read errors can cause a second close by ReverseProxy, as before; ordinary HTTP bodies tolerate this. No new reachable leak was established; small rewritten HTML's validator behavior is unchanged.
- **Local state and output.** Legacy/new session formats restore hash identity and retain state/freshness checks. Loader filters do not cap initial file/JSON allocation or session count; this is protected local state, not remote input. Replay loss is MC4-01. Viewer policy follows canonicalization. Restyled templates retain escaped text/attributes; synthetic hostile names, labels, and hostnames were escaped. No unsafe interpolation was found. Earlier trusted-upstream and Quick Tunnel hostname-ownership assumptions still apply.
