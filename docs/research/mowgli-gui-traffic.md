# MowgliNext GUI: proxy, traffic and safety research

Baseline: local `/home/bruno/mowglinext` checkout `4739f41fb4e9473da2c5a5868f4c7d1a589e7b7c`, inspected read-only on Kuffe. Citations below are paths relative to that checkout. They describe source, not measurements, deployed configuration, Cloudflare guarantees, or physical test results. The live robot may run a different revision. KB below means 1,000 bytes.

## Routing and trust boundary

Gin serves on DB `system.api.addr`, default `:4006` (`gui/pkg/providers/db.go:41`, `gui/pkg/api/api.go:18`). Global middleware permits all CORS origins, including WebSockets (`gui/pkg/api/api.go:24`); it is not authentication. The WS upgraders compare parsed `Origin` host **including port** exactly with request `Host`; missing Origin is accepted, so this is browser-origin protection, not client authentication (`gui/pkg/api/mowglinext.go:50`, `gui/pkg/api/containers.go:108`). Preserve the external Host (and Origin), including any nondefault port, across *all* proxy hops. CORS `*`, unauthenticated REST, no-Origin WS and powerful controls make private upstream reachability and a separate authentication/authorization boundary essential. Protect the static app, every API method, upgrade, tile and fallback, not just `/` or selected REST paths. Origin/CSRF controls must also protect authenticated state-changing requests; do not rely solely on the backend WS check. No GUI login, session verification or bearer-token middleware is registered (`gui/pkg/api/api.go:24`).

`/` serves configured web directory as static files; `NoRoute` returns `index.html`, including for unmatched paths; HTML is no-store, `/assets/` immutable, gzip sidecars negotiated (`gui/pkg/api/web_static.go:20`). Root absolute paths require serving at `/`. Optional `ANY /tiles/*proxyPath` is registered only when `system.map.enabled` is true (`gui/pkg/api/api.go:63`, `gui/pkg/api/tiles.go:45`); Swagger is `GET /swagger/*any` (`gui/pkg/api/api.go:70`). Be aware that unrecognized URLs may return HTML 200, not API 404. The Gin API routes are under `/api` (`gui/pkg/api/api.go:38`); full registered inventory follows. A bracket means each listed method/path exists, not all possible combinations.

Dangerous operations include teleop publishing and ROS service calls (motion, blade, emergency), destructive map/settings/parameter changes, flash, GNSS reset, drive tuning, remote-access setup, host reboot/shutdown, update/rollback, Docker start/stop/restart and rosbag actions. Container commands explicitly allow only those three verbs, not a general shell (`gui/pkg/api/containers.go:74`); internal Docker exec exists for specific tools, which must not be confused with an exposed arbitrary exec route. Updater is a distinct internal service with `/v1/*` routes (`gui/pkg/updater/server.go:47`), accessed through the GUI updater proxy, not mounted as `/v1/*` on port 4006 (`gui/pkg/api/updater.go:64`). Treat all authorization as privileged robot administration, including secrets in configuration responses; inspect exactly which fields are returned before designing logs or redaction.

## Browser addressing and persistence

With no build-time override, API fetches use relative paths and WS uses `window.location.host`, choosing `wss` for HTTPS (`gui/web/src/utils/apiHost.ts:15`). The generated client's misleading `//localhost:4200/api` default (`gui/web/src/api/Api.ts:471`) is overridden by the app singleton to `/api` (`gui/web/src/hooks/useApi.ts:4`). `:4006` in the settings UI is the *server listen-address default*, not a suffix added to the browser hostname (`gui/web/src/hooks/useSettings.ts:48`, `gui/pkg/providers/db.go:41`). Therefore an ordinary production build served at `https://robot-x.example.com/` should use HTTPS and `wss://robot-x.example.com` on 443 unchanged, assuming correct proxy/auth and Host preservation. This is a source-based conclusion, not an end-to-end test. A build with `VITE_API_HOST` is an exception: `httpBase()` explicitly creates `http://`, causing mixed content on HTTPS, and the override can also cause an Origin/Host mismatch (`gui/web/src/utils/apiHost.ts:11`). Vite's `localhost:4006` target is development-only (`gui/web/vite.config.ts:5`).

Manifest is root-relative (`gui/web/index.html:21`, `gui/web/public/manifest.json:1`); the source search did not find a service worker registration. Existing localStorage preferences (language, theme/display, time zone) are origin-scoped and will start fresh on the new hostname (`gui/web/src/i18n/index.ts:18`, `gui/web/src/theme/ThemeContext.tsx:16`, `gui/web/src/hooks/useTimeFormat.tsx:16`). Proxy authentication cookies must work for same-origin navigation, fetch, streamed POST and WS upgrade, and across expiry/reconnect; do not assume browser WebSocket can attach a custom Authorization header. Validate login redirects for fetch/WS, since a login HTML response is not an API/WS response. No backend GUI session cookie was identified. Fleet UI peer links explicitly use `http://` and the peer address (`gui/web/src/pages/FleetPage.tsx:122`): these links leave the authenticated origin and can be unreachable or insecure, even though the local fleet page itself works. The legacy `http://localhost:11311` entry in settings is a ROS master setting, not the browser API base (`gui/web/src/hooks/useSettings.ts:132`). External map tiles or other third-party calls need deployment-specific CSP/network verification.

## Streams, data volume and subscriptions

Browser topic subscriptions normally share one multiplex WS per tab: client JSON `subscribe`/`unsubscribe`, server binary MessagePack `{topic,data}`; numbers compacted, `path.xy` float32, no required JSON/base64 decoding (`gui/pkg/api/mowglinext.go:361`, `:389`, `:403`). The alternate `/subscribe/:topic` endpoint sends base64 text JSON (`gui/pkg/api/mowglinext.go:517`); normal `useWS` converts topic URIs to multiplex subscriptions (`gui/web/src/hooks/useWS.ts:27`). Publish and logs have dedicated sockets. Both server upgraders omit `EnableCompression`, whose Gorilla default is false; permessage-deflate is not enabled by these upgraders (`gui/pkg/api/mowglinext.go:50`, `gui/pkg/api/containers.go:108`). Static gzip is unrelated. Forward binary frames faithfully and do not count on WS compression.

Server coalesces each slow topic to latest message and enforces maximum rates as follows (`gui/pkg/api/mowglinext.go:93`, `gui/pkg/providers/ros.go:90`):

| Topic keys / message | Delivery limit and size information |
|---|---|
| `gps` NavSatFix, `gnssStatus`, `pose` Odometry, `imu` Imu, `ticks`, `wheelOdom` Odometry | 100 ms / up to 10 Hz each; nested numeric objects, size and actual publisher rate vary. |
| `lidar` LaserScan | 100 ms / up to 10 Hz; `ranges` and `intensities` arrays of float32 at ROS source (`gui/pkg/msgs/sensor/types_generated.go:20`); actual sample counts depend on hardware. The dashboard includes status, high-level status, power, emergency, diagnostics snapshot and mow-progress (`gui/web/src/pages/MowgliNextPage.tsx:56`, `:128`, `:199`). The map subscribes to pose, full map, path, plan, lidar, obstacles, both grids and status (`gui/web/src/pages/map/hooks/useMapStreams.ts:381`). The client ref-counts subscriptions and unsubscribes when last listener leaves, disconnect cleans up (`gui/web/src/hooks/multiplexedSocket.ts:105`, `gui/pkg/api/mowglinext.go:464`). On entering map editing it stops several streams (`gui/web/src/pages/map/hooks/useMapStreams.ts:360`); do not assume every heavy stream stops there without checking each cleanup. Crucially LiDAR remains subscribed even after the LiDAR map is present: it skips rendering on receipt, not upstream transmission (`gui/web/src/pages/map/hooks/useMapStreams.ts:250`, `:386`). Downsampling to roughly 90 points is rendering-only (`gui/web/src/pages/map/hooks/useMapStreams.ts:218`).

**Illustrative estimates, not observed measurements or upper bounds**, per active browser tab, downstream payload only; exclude TLS/TCP framing, HTTP, tiles, compression, reconnect snapshots and other tabs. Source does not determine grid dimensions, publish rate or scan samples, so values cannot be predicted reliably:

| Scenario | Explicit assumed workload | Arithmetic / estimated KB/s |
|---|---|---|
| Dashboard idle, grid quiet | 4 small telemetry topics at 1 Hz × 0.5 KB plus 10-second 5 KB HTTP snapshot | ~2.5 KB/s; if grid emits, add its full size × rate. |
| Live map, 200 × 200 grid | baseline 2.5; 40 KB full progress grid once/s; pose 1 KB × 10/s; 360-range scan, 3 KB × 10/s; other data 5 KB/s | ~87.5 KB/s; add LiDAR map on publication and changed full-map bursts. A 1 MB map every 5 s adds ~200 KB/s average while changing. |

MQTT schedules use a separate broker connection (`gui/pkg/api/schedule_mqtt.go:17`); Foxglove `:8765` and teleop relay `:8766` are backend-to-ROS channels, not browser rosbridge/MQTT passthrough (`gui/CLAUDE.md:3`). No browser camera/video or PointCloud2 streaming endpoint was found in the registered GUI topic map; scan is LaserScan, while fleet point clouds exist locally in ROS (`gui/pkg/providers/ros.go:29`, `docs/MULTI_ROBOT.md:139`).

## Long connections, uploads and downloads

Normal browser multiplex socket has no application ping identified; continuously publishing topics normally keep traffic flowing, but latched-only, inactive publisher, quiet logs and idle joystick can exceed a hypothetical 100 s idle limit. A 30 s silence watchdog closes/reconnects only when a continuous topic is subscribed; reconnect resubscribes with 1 s exponential backoff capped at 30 s (`gui/web/src/hooks/multiplexedSocket.ts:33`, `:159`, `:244`, `:290`). Dedicated publish/log sockets use infinite reconnect with the same capped backoff (`gui/web/src/hooks/useWS.ts:65`). An idle timeout can interrupt operations and require reconnect; do not infer a universal Cloudflare timeout from the premise. WS server writes have a five-second deadline on multiplex (`gui/pkg/api/mowglinext.go:26`, `:423`). Fleet's separate Go peer client sends ping every 8 s and uses 20 s read deadline (`gui/pkg/providers/fleet_peer_client.go:27`, `:181`); this does not apply to browser sockets.

The flash endpoint is a streamed POST with actual SSE stage/message/end/error events, despite logs' Swagger `text/event-stream` annotation describing a WebSocket (`gui/pkg/api/setup.go:38`, `:60`, `gui/pkg/api/containers.go:99`). Permit unbuffered streaming and suitably long-lived requests. Flash receives JSON configuration and obtains/uses firmware server-side, not a documented browser firmware binary upload (`gui/pkg/api/setup.go:49`). OpenMower import reads an entire JSON body without a route-local explicit size cap (`gui/pkg/api/openmower_import.go:169`, `:187`); set a compatible deliberate proxy limit. Rosbag download streams a potentially large generated `.tar.gz` (`gui/pkg/api/rosbag.go:417`); no fixed maximum was derived. Updater requests are limited to 8,192 bytes and responses copied up to 4 MiB (`gui/pkg/api/updater.go:91`). Normal status refreshes are polling; no other SSE or long-poll endpoint was identified in the registered API.

## Existing remote access, fleet and safety

The optional Tailscale sidecar exposes the otherwise unauthenticated GUI only to tailnet members per ACL; it explicitly does not configure public Funnel (`gui/pkg/providers/remote_access.go:20`). Serve terminates HTTPS and proxies to localhost while preserving Host (`gui/pkg/providers/remote_access.go:375`); access keys are separately stored and masked in responses (`gui/pkg/providers/remote_access_config.go:13`, `:78`, `:130`). Fleet peers assume trusted networks: peer registration and control use ordinary GUI APIs, peer client constructs plain `ws://` and corresponding HTTP endpoints, no browser identity or Access cookie (`gui/pkg/providers/fleet_peer_client.go:148`, `docs/MULTI_ROBOT.md:55`). Putting an interactive Access login in front of a peer URL will not automatically authenticate robot-to-robot fleet traffic. Retain a properly isolated trusted peer network or design explicit machine identity; do not expose unauthenticated peers publicly.

The physical emergency latch and motor gating are in STM32 firmware; `twist_mux` describes firmware as the e-stop authority (`ros2/src/mowgli_bringup/config/twist_mux.yaml:26`, `:41`), and firmware has a 200 ms cmd_vel watchdog (`firmware/stm32/ros_usbnode/src/ros/ros_custom/cpp_main.cpp:267`, `:987`). ROS collision monitoring/navigation and behavior tree remain local. The GUI is not the physical emergency stop and remote connectivity must not be the sole emergency stop. However **do not claim every safety-relevant function is GUI-independent**: the Go fleet coordinator issues proximity yield stop/resume and publishes peer poses for ROS local obstacles (`gui/pkg/providers/fleet_coordinator.go:267`, `:302`, `docs/MULTI_ROBOT.md:139`); losing the GUI process or peer links can degrade fleet coordination. A remote browser or tunnel disconnect is distinct from stopping that local backend. Confirm the deployed configuration and failure behavior for a particular fleet.

Teleop travels over `GET /api/mowglinext/publish/:topic`; the parameter is ignored and all valid JSON goes to `/cmd_vel_teleop` (`gui/pkg/api/mowglinext.go:304`). The joystick sends at 10 Hz while held, sends zero on release, and caps inputs at 0.25 m/s and 0.6 rad/s (`gui/web/src/pages/map/hooks/useManualMode.ts:5`, `:102`). ROS teleop mux lane expires after 0.5 s (`ros2/src/mowgli_bringup/config/twist_mux.yaml:26`); it is a priority timeout, not a guaranteed end-to-end stop time, since another lane may become active and mux output may refresh firmware. A delayed queued nonzero command could extend motion; no proven end-to-end bound or remote dead-man guarantee is established here. Manual blade control is held by the local behavior tree, not simply the browser joystick interval (`gui/web/src/pages/map/hooks/useManualMode.ts:75`). Tunnel latency, jitter, disconnect and stop behavior require target-system validation before relying on remote manual control. No hardware test was performed.

## Requirements for the Connect proxy

- [ ] Authenticate and authorize every path and HTTP method, including WS upgrades, static assets, SSE, tile proxy and SPA fallback; enforce a suitable CSRF/origin policy for cookie-authenticated mutations.
- [ ] Keep origin GUI port inaccessible from untrusted clients; protect any alternate LAN, Tailscale, Docker, fleet and updater paths according to their own trust boundary.
- [ ] Serve the application at the HTTPS origin root; preserve exact public Host and browser Origin end-to-end, without forcing `:4006` or rewriting Host to localhost.
- [ ] Support HTTP/1.1 Upgrade with binary and text WS frames, transparent duplex messaging and sufficiently large frames; do not rely on permessage-deflate.
- [ ] Support quiet long-lived sockets, reconnect/resubscribe and auth expiry; account for idle closures and do not replay/queue stale teleop commands.
- [ ] Stream firmware POST SSE and large rosbag downloads without unbounded buffering; allow appropriately sized JSON map imports and define explicit sensible limits.
- [ ] Preserve request/response semantics, cache controls, gzip/Vary and same-origin cookies; avoid caching authenticated API data or replacing failed API/WS requests with login HTML.
- [ ] Plan capacity from measured per-tab WS frame rates and full-grid/map bursts, plus concurrent tabs, logs, tiles and downloads; the estimates above are not measured limits.
- [ ] Keep fleet peer authentication/networking separate from interactive browser login, and validate fleet safety dependencies if the backend or peer network changes.
- [ ] Treat movement, blade, flash, update, settings and remote access as privileged operations; test tunnel latency, disconnect and physical stopping behavior on the actual deployment before remote teleop use.
